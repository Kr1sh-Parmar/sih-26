Instructions for Claude Code working in this repository.

---

## What this project is

An offline, CPU-only identity document screening system for border checkpoints (SIH PS 26188, Ministry of Home Affairs / Sashastra Seema Bal). It reads a document, validates it at three levels of certainty, checks for tampering, matches the holder's face, and gives a border officer a colour-coded verdict with checkable reasons.

Read `context/CONTEXT.md` for the domain. Read `context/CONTRACTS.md` before touching anything that crosses a module boundary.

---

## Hard rules — do not violate these without asking

**1. No UIDAI. No government APIs. Ever.**
No UIDAI certificate, key, endpoint, or database. No Aadhaar authentication or eKYC. No Interpol, no Passport Seva. If a task seems to need one, the answer is the reference issuer in `issuer/` or a local table. Flag it, do not improvise.

**2. CPU only.**
No CUDA, no `torch.cuda`, no `device='cuda'`, no GPU-only libraries (vLLM, TensorRT). Every model is ONNX Runtime on CPU. If a model cannot run on CPU in under 2 s, it does not go in.

**3. Fully offline at inference.**
Zero network calls in the screening path. Models are baked into the Docker image and loaded at startup. No `huggingface_hub.download` at runtime, no Roboflow hosted inference, no remote OCR. Roboflow is build-time only.

**4. No real government documents, ever.**
No real Aadhaar, PAN, passport, Voter ID, or DL images or numbers in any dataset, fixture, test, or commit. Everything is generated by `data/generator/`. The only real biometric anywhere is team face images for threshold calibration, held under consent, never committed.

**5. Never store raw ID numbers.**
Salted hash plus last four digits. This applies to fixtures and tests too.

**6. Decode once.**
`ctx.image` is built by the orchestrator. No module opens a file, re-reads bytes, or re-decodes. If you need a different resolution, derive it from `ctx.image`.

**7. `issuer/` is not importable from `api/`.**
The reference issuer is out-of-band tooling. It writes public keys into the trust anchor store during setup and is never called at inspection time.

**8. Contracts in `context/CONTRACTS.md` are frozen.**
`Signal`, `ScreeningContext`, `Finding`, the profile schema. If a change seems necessary, stop and say so — do not edit them to make the current task easier.

## Architecture in 60 seconds

Nine layers, one process. Client → orchestration (decode once, route by document profile) → preprocess → four modules → risk gate → fusion → officer console.

Two tiers:
- **Tier 1** runs on every document, under 1 s: extraction, validation, cheap tampering, 1:1 face.
- **Tier 2** fires only when the risk gate escalates (~15%): deep forensics, active liveness, 1:N gallery.

Every check emits a `Signal`. Fusion groups correlated signals into `Finding`s by anchor, scores by trust class, and produces evidence cards.

**Three trust classes** — this is the core idea of the whole system:

| Class | Meaning |
|---|---|
| `cryptographic` | Ed25519 signature verifies against a trusted key. Certain. |
| `arithmetic` | Deterministic check, no ML, no key. MRZ check digits, Verhoeff, date logic. |
| `probabilistic` | Inference. Tamper heuristics, face match, OCR confidence. Can be wrong. |

Cryptographic passes suppress probabilistic findings that dispute the *signed fields*.

## Code conventions

**Modules return `list[Signal]`. Nothing else.** No images, no dicts, no exceptions-as-control-flow.

```python
def check_mrz_checkdigits(ctx: ScreeningContext) -> list[Signal]:
    ...
```

**Validation layers are pure functions.** `(ctx) -> list[Signal]`, no I/O, no mutation beyond appending signals. They must be unit-testable with a hand-built context.

**Never write `weight` into a Signal.** Weights come from the profile at fusion time. A signal does not know its own importance.

**`evidence` strings are read by a border officer.**

```python
# good
evidence=f"MRZ date of birth {mrz_dob} does not match printed {viz_dob}"
# bad
evidence="viz_mrz_dob_mismatch=True"
```

**Signal IDs are stable dotted strings** registered in `context/CONTRACTS.md` §1. They appear in weights, tests, and audit logs. Do not rename one without updating every profile.

**Models load once at startup** via `core/registry.py`. Never construct an ONNX session inside a request handler.

**Time everything.** Every module sets `latency_ms` on its signals. The latency budget is a requirement, not a hope.

**`inconclusive` is not `pass`, and `not_applicable` is not `inconclusive`.**
- Aadhaar has no MRZ → `not_applicable`, excluded from coverage.
- MRZ too blurred to read → `inconclusive`, counts against coverage.
Getting this wrong means a blurry photo produces a GREEN verdict.

## Things that look like bugs but are deliberate

| Looks wrong | Why it is right |
|---|---|
| ELA weighted only 0.30 | It is a fragile signal — recompression flattens it. It exists as an officer-facing visualisation. |
| No stamp template library | Thousands of variants, no public reference set. Replaced by duplicate detection and date logic. |
| Metadata checks skipped on scanner input | The scanner writes the file, so EXIF is clean by construction. Only fires on uploads. |
| Face score is not 0–100 | `((cos+1)/2)*100` maps a stranger to 50. Misleading in the direction that admits fraudsters. |
| Document blur threshold is looser than live blur threshold | Printed photos are naturally softer than camera captures. |
| One field detector for six document types, not six detectors | Shared classes generalise better; one warm session instead of six. |
| Reference issuer signs Aadhaar too | We have no UIDAI access. Aadhaar is treated like the other five. See `context/CONTEXT.md` §5. |

## Common tasks

**Adding a validation check**
1. Add the signal ID to `context/CONTRACTS.md` §1
2. Write a pure function in the right `modules/validation/layer_*.py`
3. Add reliability weight to `config/reliability.yaml`
4. Add to the relevant profile's `arithmetic` or `checks` list
5. Unit test with a hand-built `ScreeningContext`

**Adding a document type**
1. New YAML in `profiles/`
2. Map its fields onto the existing 22-class ontology — **do not add classes without discussion**
3. Declare `forbidden_classes` (a class that should never appear on this document)
4. Add a template to `data/templates/` and generator rules
5. Set `verify.signature` and `disclosure`

**Adding a model**
1. Export to ONNX, quantise int8, measure CPU latency
2. If it exceeds its share of the budget, it does not go in
3. Register in `core/registry.py`, loaded at startup
4. Commit the weights to `models/` so the Docker image is self-contained

## Testing

- Validation layers: pure-function unit tests, hand-built contexts, no fixtures on disk
- MRZ parser: test against the ICAO 9303 published examples plus deliberate check-digit failures
- Fusion: property tests — hard fail always wins; coverage below floor never returns GREEN; crypto pass suppresses probabilistic findings on signed fields
- Tampering: train on one mutation family, **test on a different one**, report both numbers
- Face: report FAR/FRR on the doc-vs-live calibration set, plus demographic breakdown on FairFace

Never commit a test fixture containing a real document.

## When you are unsure

Ask rather than assume, especially about:
- Anything that would touch the network at inference time
- Anything that would need a GPU
- Anything that would store or log an ID number or a face image
- Any change to a frozen contract
- Any accuracy claim that would go in the pitch

State assumptions inline in the code as comments rather than silently picking one.
